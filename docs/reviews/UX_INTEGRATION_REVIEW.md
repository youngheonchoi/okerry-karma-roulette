## 2. 화면 구조

독박: UX-01 → UX-02 → UX-03/04 반복 → UX-05 → UX-06 → UX-07 → UX-08.

N빵: UX-01 → UX-02 → UX-02A → UX-03/04 반복 → UX-05 계산 → UX-07 → UX-08.

## 3. 디자인 결정 및 근거 — Q02

정산 결과 UI는 확정된 참가자별 정수 금액 배열을 표시한다. 점수 비율과 보정 후 실제 금액을 분리하며, 어떤 안에서도 합계=총액·정수·비음수를 검증한다.

- PM A: 총액이 인원×100원 이상이면 각 이상액을 가장 가까운 100원으로 반올림한 뒤 전체 차액을 최고점자 한 명에게 반영한다. 동점은 등록순 첫 사람이다. 총액이 기준 미만이거나 보정 결과가 음수이면 A 전체를 폐기하고 B로 다시 계산한다. 정확히 50원은 절반 올림 권고이며 미확정이다.
- UX B: 모든 총액에 최대잔여법을 적용한다. `bᵢ=floor(T×sᵢ/W)`, `R=T−Σbᵢ`. 정확한 나머지 `(T×sᵢ) mod W`가 큰 순으로 R명에게 1원씩 더하고, 동률은 등록순이다. 화면 반올림 비율로 정렬하지 않는다.
- USER_FLOW의 기존 대안인 ‘음수이면 다음 참가자로 보정 이동’은 PM A의 ‘전체 B 전환’과 다르다. PM A를 인용할 때 해당 문장을 그대로 사용하면 안 된다.
- UX는 B를 계속 권고한다. 큰 총액에서도 같은 점수 참가자 한 명에게 차액이 집중되지 않아 설명이 단순하다. 이는 정책 승인이나 원문 100원 규칙의 변경 확정이 아니다.

| 정책 비교 입력 | A 기대값 | B 기대값 |
|---|---|---|
| 1원, 100점×12명 | 저액으로 B 전환: 첫 사람 1원, 나머지 0원 | 첫 사람 1원, 나머지 0원 |
| 300원, 100점×2명 | 절반 올림 가정: 100원/200원 | 150원/150원 |
| 99,999,999원, 100점×12명 | 첫 사람 8,333,699원, 나머지 각 8,333,300원 | 1~3번 각 8,333,334원, 나머지 각 8,333,333원 |

위 값은 문서 계산 예시이며 실행 검증 결과가 아니다. A의 300원 사례는 반올림 경계와 동점 보정 순서를 드러낸다. PM/QA가 선택한 안의 기대값만 최종 수용 기준으로 사용해야 한다. OPEN_QUESTIONS의 B 설명 중 ‘나머지 내림값’은 ‘정확한 나머지가 큰 순’으로 정리할 것을 제안한다.

## 4. 컴포넌트와 상태 정의 — Q03 조건부 제안

결과에서 접혀 있다는 사실만으로 참가자의 공개 허용이 확보되지는 않는다. PM Q03 A의 ‘공개 선택한 주요 질문만 표시’와 C의 ‘참가자별 동의’는 현재 구분도 불명확하다. 공개 주체·선택 시점·문항별 또는 참가자별 허용 범위·철회를 한 계약으로 결정해야 한다.

아래는 PM 권고안을 채택하는 경우의 구체화 제안이다. 현재 확정 요구나 구현 지시가 아니다.

| 위치·상태 | 동작 제안 | 경계 |
|---|---|---|
| UX-04 응답 중 | 기존 기준으로 주요 질문 후보 최대 3개를 본인 화면에 표시하고 후보별 공개 선택 제공. 기본 모두 미선택 | 절댓값 큰 순·동률 원문순. 후보가 바뀌면 새 후보는 자동 동의하지 않음 |
| UX-04 공개 선택 | `선택한 질문은 결과에서 모두 볼 수 있어요` 안내, 공개 선택 없이도 응답 완료 가능 | 질문 공개가 점수·확률·금액에 영향 없음 |
| UX-04 완료 전 취소 | 공개 선택을 자유롭게 해제 가능 | 응답 완료와 공개 선택을 하나의 필수 동의로 묶지 않음 |
| UX-07 기본 접힘 | 공개 허용된 후보만 펼침 대상. 조작명 `공개된 주요 질문 보기` 제안 | 한 사람의 전체 펼침 조작을 타인의 동의로 간주하지 않음 |
| UX-07 허용 0개 | `공개된 주요 질문이 없어요` 표시 | 다른 참가자가 질문 선택 0개인지 공개 거부인지 추론할 문구를 표시하지 않음 |
| UX-07 철회 | 참가자별 `질문 공개 숨기기` 제안. 질문을 즉시 DOM·접근성 트리에서 제거 | 이미 본 내용을 되돌릴 수 없음. 재공개·완료 응답 수정은 이 제안에 포함하지 않음 |
| UX-08 공유·복사 | 공개 선택·펼침 상태와 무관하게 질문·질문 ID·응답 모두 제외 | 독박 당첨자 점수·확률, N빵 전원 부담액 등 원문 필수 필드는 유지 |
| 재진행 | 질문 공개 선택·철회·펼침 상태 모두 초기화 | 같은 참가자도 이전 동의를 재사용하지 않음 |

인증 없는 한 기기 방식이므로 위 선택은 본인 인증이 아니며 다른 사람이 버튼을 누르는 행위나 OS 캡처를 차단하지 못한다. 결과 공개 정책을 정하기 전에는 이 제안을 최종 동의 설계로 표현하지 않는다.

## 5. 반응형 및 접근성 고려사항

- 기존 SCREEN_SPEC의 조작 48×48px 이상, 인접 간격 8px, 본문 16/24px, 보조 14/20px 기준을 유지한다. 질문·공개 선택은 체크박스 의미와 전체 라벨 조작을 제공한다.
- 320px 화면의 좌우 16px 여백을 빼면 본문은 288px다. 참가자 입력 행은 `번호24 + 간격8 + 입력200 + 간격8 + 삭제48 = 288px`로 명확히 기재하고 랜덤 이름은 다음 줄에 둔다.
- 12명과 200% 글자 확대에서 세로 흐름을 유지하고 긴 닉네임은 줄바꿈한다. 참가자 목록을 좁은 표로 압축하지 않는다.
- 질문 비허용·접힘·철회 상태는 시각적 가림만 적용하지 않고 DOM·접근성 트리 노출을 제어한다. 펼침 상태와 체크 상태는 별도로 전달한다.
- 실제 화면을 만들거나 수정한 작업은 아니므로 이번 산출물에 화면 캡처와 실행 합격 판정은 없다.

## 6. 개발 전달 사항

1. Q02·Q03 결정 전 최종 계산 함수·공개 동작을 고정하지 않는다. 결과 UI는 하나의 확정 결과를 소비하고 공유도 같은 금액 배열을 사용한다.
2. F08은 응답·점수100점·결과·공개 상태를 초기화하고 첫 참가자 호출부터 새 라운드를 진행한다. 기존 당첨자로 바로 되돌아가는 경로를 만들지 않는다.
3. 정책 결정 후 OPEN_QUESTIONS → FUNCTIONAL_SPEC → USER_FLOW/SCREEN_SPEC → PRD/TASK_BACKLOG 및 QA 기대값을 함께 갱신한다.
4. 원문 대조·문서 교차 검토와 정책 승인·실제 UI/계산 검증을 별도 상태로 기록한다. 이번 검토에서 PM 문서와 QA 의견서는 직접 수정하지 않았다.

## 가정

이번 지시를 팀장 통합 보고에 대한 UX 교차 검토와 후속 명세 제안 업무로 해석했다. 정책 승인 권한을 위임받은 것으로 해석하지 않았다. 공동 문서의 변경이 관찰돼 덮어쓰기를 피하고 별도 검토본으로 제출한다. 기존 두 UX 문서의 v0.4 갱신 시도는 적용 검증 실패로 저장되지 않았으며 최종 버전은 v0.3이다.
